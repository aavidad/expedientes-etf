# F0.10: perfiles y administración de usuarios

`0002_perfiles.sql` depende de identidad 0001 y catálogo 0002. Añade concesiones
con vigencia, adscripciones con FK al catálogo, exclusión de intervalos solapados
y una marca única del administrador inicial. Las tablas tienen RLS forzada;
`etf_app` lee sólo sus propias filas o las autorizadas a Administración. Las
escrituras pasan por funciones que revalidan el perfil vigente y confirman el
cambio con su auditoría.

`ETF_PRIMER_ADMINISTRADOR` contiene el login normalizado de AD. Tras autenticar
su identidad estable se concede el perfil una sola vez. La marca y la concesión
se confirman con el alta de sesión. Retirar el perfil, reiniciar o cambiar esta
variable no permite repetir el alta inicial. La recuperación exige soporte
expreso y auditado, como establece el esquema del backend.

La API ofrece `GET /api/admin/usuarios` y `PUT /api/admin/usuarios/{id}/perfiles`.
El cambio envía `version`, `estado` (`activo` o `baja`), `perfiles` y `equipo`.
Cada perfil lleva `perfil`, `desde` y `hasta` opcional, en formato RFC 3339. El
equipo lleva `equipo_id`, `puesto` (`ts`, `es`, `ps`) y las mismas fechas que el
perfil profesional. Las concesiones nuevas comienzan como pronto en el momento
de confirmación. Retirar un perfil o cambiar de equipo cierra el intervalo
anterior; no elimina su historia. Una clave técnica identifica cada fila histórica, también cuando se cancela una concesión futura. Los intervalos vacíos cancelados no aparecen en la configuración vigente. Una configuración activa sin perfil vigente
muestra la pantalla de pendiente de alta. Un conflicto devuelve 409 y la versión
actual; la pantalla permite consultar los permisos antes de volver a guardar.

La comprobación SQL usa el perfil y la hora actuales después de adquirir el bloqueo, para denegar también una petición que estuviera esperando cuando se retira el permiso.

El middleware relee la sesión en cada petición, exige el perfil declarado y
valida CSRF en la escritura. Las rutas de negocio sin permiso declarado quedan
cerradas. Administración sola no recibe acceso a expedientes ni a Memoria,
SPAF o comisiones. El menú combina los perfiles en el orden del flujo; las
secciones de negocio futuras muestran su estado pendiente.

Para repetir el ensayo con PostgreSQL 18, LDAPS y Chrome del sistema:

```bash
ETF_NAVEGADOR_INTEGRACION=1 ETF_EVIDENCIA_RUTA=/tmp/etf-f010-evidencia \
  ./internal/adaptadores/postgres/testdata/ensayar-identidad.sh
make ci
```

El ensayo aplica la versión anterior, la nueva, la repetición sin cambios y el
conjunto desde cero. Comprueba vigencias, concesión inicial concurrente,
reversión por fallo de auditoría, FK y adscripción única. La prueba de aislamiento
usa una tabla sintética temporal con RLS de dos equipos: aún no existe el módulo
de expedientes. Sus políticas y claves compuestas se verificarán al incorporarlo.
Chrome prueba pendiente → asignación → menú, traslado y baja, denegaciones,
conservación de cambios sin guardar, Atrás y Adelante, teclado, privacidad, ambos idiomas y alto contraste a 1024, 390 y 256 píxeles.
Las capturas y trazas se guardan fuera del repositorio. El contenedor y su
almacenamiento desechable se eliminan al terminar.
